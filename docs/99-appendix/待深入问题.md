## ★★ 如果只做三件事,按这个顺序

| 优先级 | 做什么 | 为什么是这个顺序 |
|---|---|---|
| **1** | 🔴 **加鉴权**(API Key 或 JWT) | ★★ **不鉴权的网关是给别人开的** —— 你的 key 会被陌生人烧光 |
| **2** | 🔴 **限流维度做成可信的** | ★ 现在的 `X-Client-Id` ★ 客户端自己说了算,**换个头就绕过** |
| **3** | 🟡 **加熔断 + metrics** | ★ 让"上游挂了"能被**快速发现**,而不是每个请求白等 30 秒 |

```text
★★ 为什么前两条都是【安全】?
   因为这个项目的定位是"网关",★ 而网关的第一职责是【守住后门】。
   ★ 一个功能齐全但不设防的网关,比一个功能残缺但设防的网关危险得多。
```

## 🔴 A. 安全(最严重的一类)

### A1. ★★ 网关对外**完全没有鉴权**

```text
★ 现象:POST /v1/chat/completions ★ 任何人都能调,★ 不需要任何凭证
★★ 后果:★ 只要知道你的地址,陌生人就能【用你的 API key 烧你的钱】
   ★★ 而且 From 你的账单 → ★ 你发现的时候钱已经没了
```

**怎么做**

```text
① 最简:客户端带 Authorization,网关校验一个共享密钥(★ 常量时间比较,防时序攻击)
② 正经:接 JWT/OAuth2 → ★ 按用户/租户限流,而不是按 IP
③ ★ 关键改动点:★ 一个新 WebFilter,★ 顺序排在 RateLimitWebFilter 【之前】
   ★★ 顺序很关键:★ 没通过鉴权的请求,不该占用限流额度
```

> ★★ **面试话术**:「这是本项目最大的缺口 —— 我做了限流但没做鉴权,而**限流是在'你已经被允许进来'的前提下才有意义的**。正确顺序是先认证、再限流。」

### A2. ★ 限流的 `X-Client-Id` 是**客户端自报的**

```text
★ 现象:限流按请求头 X-Client-Id 分桶
★★ 后果:★ 攻击者每次换一个 X-Client-Id → ★ 每个桶都是满的 → 限流【完全失效】
   ★★ 更糟:还可以【冒充别人】的 ID 把别人的额度打满(★ 定向拒绝服务)
```

**怎么做**

```text
★ 根因:★ 身份不能由被限流方自己声明 —— ★ 这是"限流"和"防刷"的分界线
★ 怎么办:① 先做 A1(鉴权),★ 用【鉴权后的身份】当限流维度
         ② ★ X-Client-Id 只能作为"已认证用户内部的细分",★ 不能当身份
```

> ★★ **面试话术**:「我已经意识到 `X-Client-Id` 是客户端可控的 —— **一个可以被客户端单方面改掉的限流维度,等于没有限流**。正确做法是用鉴权后的主体 ID。」

### A3. ★ `X-Forwarded-For` 故意没信,但也没做**可信代理链**解析

```text
★ 现状:★ 直接取远端地址 → ★ 反代之后所有请求都是同一个 IP → 限流维度退化成"全局"
★ 为什么不做:★ 因为【盲信 XFF 比不信任更危险】(★ 攻击者可以随便伪造)
   ★★ 正确做法:★ 只信任【已知的可信代理】写入的那一段,★ 而不是整条链
```

**怎么做**

```text
★ 引入一份"可信代理 IP 白名单",★ 从右往左剥,直到遇到不可信的为止
★ 改动点:RateLimitWebFilter#resolveClientId
```

> ★ 这条已经在 [类-RateLimitWebFilter-深入](../01-modules/06-限流/类-RateLimitWebFilter-深入.md) 交代过。

## 🟡 B. 高可用

### B1. ★★ 没有熔断器 / 降级

```text
★ 现象:上游某家厂商挂了/变慢
★★ 后果:★ 每个请求都要【白等 30 秒】(read-timeout)才失败
   ★★ 而 WebFlux 事件循环线程就那么几个 → ★★ 慢会累积成" весь 网关都不可用"
   ★★ 一句话:★ 一个慢的上游,能拖垮一个健康的网关
```

**怎么做**

```text
★ 加 Resilience4j 的 CircuitBreaker:
   · 连续失败 N 次 → ★ 熔断,★ 后续请求快速失败(不再等 30 秒)
   · 冷却期后放几个请求试探 → ★ 半开状态
★ 降级策略(★ 这才是"网关"的价值):★ 一家挂了 → ★ 路由到备用的另一家
   ★★ 本项目已经具备这个能力了 —— ★ ProviderRegistry 里有多个 Provider
```

> ★★ **面试话术**:「熔断我这版没做,但**架构上是留了口的** —— 注册表里已经有多个 Provider,加一层'主备切换 + 熔断'就能把'上游挂了'降级成'自动换一家',而不是'整个网关变慢'。」

### B2. ⚠️ 没有重试(**故意的**,但企业通常要)

```text
★ 现状:上游 429/500 → ★ 网关直接返回,不重试
★ 现成的理由(见 非流式流程):★ 重试会再花一次钱,★ 而且上游 429 时重试是激化限流
★★ 但企业级网关通常要有【带退避 + 抖动】的重试:
   ★ 只重试【幂等且明确可重试】的错误(★ 5xx / 429),★ 不重试 4xx
   ★ 必须设总时长上限,★ 且有抖动(jitter)★ 否则重试风暴是自我 DDoS
```

### B3. ★ 单实例验证,多实例未验证

```text
★ 现状:所有测试都是单实例跑的
★ 理论上没问题:★ 限流状态在 Redis 里(★ 天然跨实例共享)
★★ 但没验过:★ 两个实例同时打到同一个桶,行为对不对?
   ★ 理论上 Lua 保证原子 → ★ 但"理论上"不是证据
```

**怎么做**

```text
★ 起两个应用实例 + 一个真 Redis,并发打同一个 clientId,
★ 断言 ★ 放行总数仍然严格等于桶容量
★ ★★ 这就是"把单元测试的正确性,提升到部署拓扑的正确性"
```

### B4. ⚠️ 优雅关闭:正在流的请求怎么办?

```text
★ 现象:发版时应用被 kill
★★ 后果:★ 正在生成的流【直接断掉】—— ★ 客户端看到的是"输出到一半断了"
★ 怎么做:★ 配 graceful shutdown,★ 给一个"停止接新请求、但让存量请求跑完"的窗口
   ★★ 而流式请求可能跑几分钟 → ★★ 这个窗口要多长本身是个业务决策
```

## 🟡 C. 可观测性

### C1. ★★ 没有 metrics,只有日志

```text
★★ 后果:★ 你【无法回答】这些最该被回答的问题:
   · 过去一小时被限流了多少次?   · 哪个渠道最慢?
   · 上游错误率是多少?           · P99 延迟多少?
   ★★ 日志能【事后翻】,但★ 不能【实时告警】—— 而网关出问题是要【立刻】知道的
```

**怎么做**

```text
★ 加 micrometer + Prometheus,埋这几个指标:
   ★ 网关自己的:请求量 / 延迟直方图 / 限流拒绝数(★ 按 outcome 分开)
   ★ 上游的:★ 按 channel 打标签的成功率 / 延迟 / 空闲超时次数
   ★★ 关键:★ 429 和 503 必须分开计数 —— ★ 混在一起就是"把一次 Redis 故障
      显示成一次流量高峰"(★ 和哨兵值 UNKNOWN_REMAINING 是同一个道理)
```

### C2. ★ 没有链路追踪

```text
★ 现状:每行日志有 channel=,但★ 没有贯穿一次请求的 traceId
★★ 后果:★ 一个请求经过 filter → controller → provider,
   ★ 四行日志【关联不起来】—— ★ 并发时根本对不上
★ 怎么做:★ 生成 traceId 塞进 Reactor Context,★ 每行日志带上它
```

### C3. ★ `[上游原始响应]` 打的是完整响应体

```text
★ 现状:OpenAiCompatibleProvider 用 log.info 打整个原始 JSON
★★ 两个问题:① ★ 长回复会让日志体积爆炸 ② ★ 用户内容进了日志(隐私/合规)
★ 怎么做:★ 降级到 DEBUG,★ 或只打结构和长度,★ 或做脱敏
```

## 🟢 D. 一致性与测试

### D1. ★ 限流的错误格式和 M5 不一致

```text
★★ 现状:限流的 429/503 由 RateLimitWebFilter ★ 手写响应体
   ★ 而其他错误由 UpstreamExceptionHandler 生成
   ★★ 后果:★ 两处的 error.type 字段对不上 —— ★ 客户端要写两套解析逻辑
★ 怎么做:★ 把"造错误响应"抽成一个共用组件,★ 两处都调它
   ★★ 这也是"重复实现必然分叉"的一个实例
```

> ★ 对照表在 [类-RateLimitWebFilter-深入](../01-modules/06-限流/类-RateLimitWebFilter-深入.md)。

### D2. ⚠️ `UNAVAILABLE → 503` 这条 filter 分支只验到决策层

```text
★ 现状:RateLimitFailOpenTest 验的是 limiter 返回什么【决策】,
   ★ 没验 filter 把它变成了什么【HTTP 响应】
★★ 严格说这是【测不了】而不是【没测】—— ★ 因为启动自检让
   "enabled=true 但连不上 Redis"的应用根本起不来,运行期只剩"跑到一半挂了"
★ 怎么做:★ 要覆盖它,得在应用跑起来【之后】把 Redis 杀掉 → ★ 属于故障注入测试
```

### D3. ⚠️ `ProviderConfig` 的部分失败路径未见测试

```text
★ 已有测试覆盖:默认渠道不存在 / 重名 / 空列表 / 空白名(在 ProviderRegistryTest)
★ 未见测试:★ ProviderConfig 自己的校验(★ 空 base-url 会怎样)
★ 怎么做:★ 补几条"配置错了要启动失败"的测试 ——
   ★★ 因为【装配代码】是最容易写错又最没人守的一块
```

### D4. ⚠️ 真实厂商的 API 形状未验证

```text
★★ 现状:所有测试的上游都是 WireMock 假上游 —— ★ 而假上游是【我们自己写的】
   ★★ 也就是说:★ 如果真厂商的响应和我们的假设不一样,测试【发现不了】
★ 怎么做:★ 加一个"打真上游"的冒烟测试,★ 或至少定期手工核对一次契约
   ★★ 诚实地说:★ 这是"假上游"这个手段【固有的】边界,不是实现漏洞
```

## 🟢 E. 功能

| # | 缺口 | 后果 | 怎么做 |
|---|---|---|---|
| E1 | ★ **没有 token 计量 / 成本统计** | ★ 不知道钱花在哪家渠道、哪个用户 | ★ 从 `usage` 字段采集,★ 按 channel + 用户聚合 |
| E2 | ★ **没有密钥轮换 / 多密钥** | ★ 一个 key 被限流或失效 → ★ 整个渠道不可用 | ★ 一个渠道配多个 key,★ 失败自动切换 |
| E3 | **没有配置热更新** | ★ 改限流额度要重启 | ★ 配合 Nacos/Apollo 或定时刷新 |
| E4 | **不支持 Function Calling / 多模态** | ★ Agent 场景用不了 | ★ 契约里加 `tools` 字段,★ 归一里透传 |
| E5 | **没有请求缓存** | ★ 相同问题重复烧钱 | ★ 语义缓存(★ 注意:大模型输出有随机性,缓存要谨慎) |
| E6 | **没有请求/响应大小限制** | ★ 超长 prompt 可能打爆内存 | ★ 在 filter 层限 body 大小 |

## ★★ 面试时怎么谈这些缺口

```text
★★ 原则:★ 主动说出来,比等着被问出来强得多。
   ★ 因为面试官一定能看出来 —— ★ 而你主动说 = 说明你有判断力;
   ★ 被问出来 = 说明你没想过。
```

**一段可以直接用的话**

> "这个项目我最清楚它的边界:**它做了限流但没做鉴权** —— 而限流是在'你已经被允许进来'的前提下才有意义的,所以正确顺序应该是先认证再限流。另外限流维度用的是客户端自报的 `X-Client-Id`,**一个可以被客户端改掉的维度等于没有限流**,这两个是我下一步优先要补的。再往后是熔断和 metrics —— 现在**上游挂了每个请求要白等 30 秒**,这在 WebFlux 下会拖垮整个事件循环。"

```text
★★ 这段话为什么强?
   ① ★ 说出了【为什么】没做/该做,不是罗列功能
   ② ★ 说出了【依赖关系】(限流依赖鉴权)
   ③ ★ 说出了【技术后果】(慢请求拖垮事件循环),★ 而不是"加上会更好"
```
