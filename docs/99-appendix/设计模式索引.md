## ★ 一表速览

| # | 模式 | 本项目在哪 | 一句话收益 |
|---|---|---|---|
| 1 | ★★ **适配器** | `OpenAiCompatibleProvider` | ★ 把 N 家厂商的私有格式**变成一种** |
| 2 | ★★ **策略** | `Provider` SPI | 换渠道**不改调用方** |
| 3 | **注册表** | `ProviderRegistry` | 按名查找 + **集中校验** |

## 1. ★★ 适配器(Adapter)—— 网关的技术定义

**解决什么问题**
```text
★ 甲方要求:所有客户端只用一套 SDK
★ 现实:N 家厂商的接口长得都不一样
   · 字段名不同    · 嵌套层级不同
   · 有的给 object 有的不给   · 有的偷偷换模型名
   ↓
★ 如果让客户端自己适配 → ★ 每接一家就要改一次所有客户端
```

**本项目怎么做的**
```java
// OpenAiCompatibleProvider
//   【我们的 DTO】→ 翻译成【上游要的 Map】→ 发出去
//   【上游的 JsonNode】→ normalize() → 【我们的 DTO】
//
// ★ 两端都是"我们认识的形状",厂商的形状被关在这一个类里
```

```text
★★ 一句话:★ 适配器 = 在"两种不兼容的接口"之间放一层翻译
   ★★ 而【网关】这个词的技术定义就是"一个做适配的中间层"
```

**★ 面试话术**

> "网关本质上是适配器模式:上游 N 家厂商各有各的格式,我对客户端只暴露一套 OpenAI 兼容契约。厂商改协议,改动被关在**一个 Provider 类**里,客户端零感知。"

## 2. ★★ 策略(Strategy)—— SPI 就是策略模式

**解决什么问题**
```text
★ 调用方需要"选一家厂商发请求"
★ 如果写成 if/else:★ 每加一家厂商,就要改调用方
```

**本项目怎么做的**
```text
★★ 关键设计:★ 判断逻辑【全部】移出调用方
   · ChatController 只有一行:providerRegistry.resolveOrDefault(request.provider())
     ★ 没有 if/else,★ 没有任何厂商名字
   · 加第二家厂商 + 加上路由,★ Controller 从头到尾只改了这一个表达式
   ↓
★ 这就是"SPI 抽对了"的验收标准
```

**★ 面试话术**

> "Provider 是策略接口,`OpenAiCompatibleProvider` 是策略实现。**加一家厂商只改 YAML 不改代码** —— 因为'一个实现 × N 份配置',厂商差异被降级成了数据。"

## 3. 注册表(Registry)—— 查找 + 校验的集中地

**解决什么问题**
```text
★ 策略对象有了,但"按名字找到它"这件事写在哪?
★ 散在调用方 → ★ 每个调用点都要处理"找不到怎么办",★ 而处理方式必然不一致
```

**本项目怎么做的**
```text
★ ProviderRegistry 构造时就做完全部校验(★ 3 条 fail-fast),
   之后 resolve / resolveOrDefault / names 都是**纯查询**
   ↓
★★ 收益:★ 非法状态在【构造期】就被排除 → 之后的所有查询都**不需要出错处理**
```

**★ 面试话术**

> "注册表把'校验'和'查找'分开了:构造时 fail-fast 排掉所有非法状态,运行期就只剩纯查询。**能让构造期发现的错误,不该留到调用期。**"

## 4. 责任链(Chain of Responsibility)—— `WebFilter` 链

**解决什么问题**
```text
★ 限流这件事需要在【所有业务之前】执行
★ 写在 Controller 里 → ★ 每个新端点都要记得加一遍,★ 忘一个就是一个洞
```

**本项目怎么做的**
```text
★★ WebFilter 链:请求先过 filter,再进 DispatcherHandler
   ★ 好处:★ 限流"挂"在链路上,而不是"写"在业务里
   ★★ 代价:⚠️ filter 抛的异常 @RestControllerAdvice 接不住 → ★ 得手写响应体
```

**★ 面试话术**

> "限流做成 WebFilter 而不是写在 Controller 里,是为了让它是**横切**的。代价是它跑在 Spring MVC/WebFlux 的异常处理之外 —— 所以 `RateLimitWebFilter` 必须自己写错误响应体。"

## 5. ★ 静态工厂(Static Factory)—— 让非法状态构造不出来

**解决什么问题**
```text
★ RateLimitDecision 有三个状态:放行 / 拒绝 / 限流器坏了
★ 如果暴露一个 public 构造器 → ★ 调用方可以造出"放行 但 Outcome=DENIED"这种矛盾对象
```

**本项目怎么做的**
```java
RateLimitDecision.allowed(remaining)                  // ★ 放行
RateLimitDecision.denied(remaining, retryAfterMillis) // ★ 拒绝
RateLimitDecision.unavailable()                       // ★ 限流器故障
RateLimitDecision.allowedWithoutQuota()               // ★★ 放行但水位未知
```

```text
★★ 方法名就是文档:★ 读 allowedWithoutQuota() 比读
   new RateLimitDecision(ALLOWED, -1, 0) 清楚一个数量级
```

**★ 面试话术**

> "`RateLimitDecision` 用静态工厂而不是 public 构造器,因为**方法名能表达语义、构造器不能**。`allowedWithoutQuota()` 一眼就知道是'放行但不知道还剩多少',而 `new RateLimitDecision(ALLOWED, -1, 0)` 需要你去查文档。"

## 6. ★ 模板方法(Template Method)—— 三段式骨架

**解决什么问题**
```text
★ 流式处理有三件事要做:收数据 / 处理协议尾巴 / 归一
★ 揉在一个方法里 → ★ 想单独验"空闲超时"就得把归一也一起跑
```

**本项目怎么做的**
```text
★★ chatCompletionStream = raw(传输) → filter(协议尾巴) → concatMap(归一)
   · raw ★ 是 public 的 —— ★ 刻意放开,好让 IdleTimeoutTest 直接测它
   · 每段只有一个关注点,★ 换掉任何一段不影响另外两段
```

**★ 面试话术**

> "流式我拆成三段:传输、协议尾巴、归一。**判据不是'代码太长',而是'这部分我有独立的问题想问它'** —— 空闲超时能不能杀流,是一个和归一完全无关的问题,所以它必须是独立的一段。"

## 7. 值对象(Value Object)—— 数据自己管好自己

**解决什么问题**
```text
★ 配置里的一个渠道:base-url / api-key / model
★ 如果散成三个字符串传来传去 → ★ 谁都能传一个空 base-url
```

**本项目怎么做的**
```java
public record Channel(String baseUrl, String apiKey, String model)  // ★ 没有 name 字段
public record ProviderProperties(String defaultChannel, Map<String, Channel> channels)
```

```text
★ record = ★ 天然不可变 + 自动 equals/hashCode
★★ 而 compact constructor 里做的"规范化"(null → 空 Map),★
   保证了"从构造器出来的对象一定是合法的"
```

## 8. ★ 哨兵值(Sentinel Value)—— 用特殊值表达"未知/结束"

**解决什么问题**
```text
★ 有些信息是"不存在"的:流结束了 / 水位未知
★ 用 null 表达 → ★ 到处 NPE;用 0 表达 → ★ 撒谎
```

**本项目怎么做的**

| 哨兵 | 值 | 表达什么 | ⚠️ 关键约束 |
|---|---|---|---|
| `ChatCompletionChunk.DONE_SENTINEL` | `"[DONE]"` | 流结束 | ★★ **必须是上游会发的那个字面量**,否则 filter 丢不掉 |
| `RateLimitDecision.UNKNOWN_REMAINING` | `-1` | 水位未知 | ★★ **不能是 0** —— 0 会被监控当成"额度用尽" |

**★ 面试话术**

> "水位未知时我报 `-1` 而不是 `0`。**报 0 会把一次 Redis 故障描述成一次流量高峰** —— 监控看到的是'额度用尽',而真相是'限流器坏了'。哨兵值选错,是把事故指向了错误的方向。"

## 9. 单一真相源(Single Source of Truth)

**解决什么问题**
```text
★ 渠道名同时出现在两个地方 → ★ 迟早不一致
```

**本项目怎么做的**
```text
★★ Channel 里【故意没有】name 字段
   ★ 因为渠道名已经是 Map 的 key 了
   ★ 再存一份 → ★ 两份数据,必然有一天对不上
   ↓
★ 同理:令牌桶的时间戳 ★ 只用 redis.call('TIME') 一个时钟源
   ★★ 而不是"各实例取自己的 System.currentTimeMillis()"
```

**★ 面试话术**

> "渠道名只存在一个地方 —— Map 的 key。**同一个事实有第二个副本,就一定会有一天对不上**,而且对不上的时候你查不出来哪个是对的。"

## 10. ★★ 契约式设计(Design by Contract)—— 7 处 fail-fast

**解决什么问题**
```text
★ 配置错了、依赖没了、渠道重名了 —— 这些事【总会发生】
★ 问题是:★ 什么时候被发现?
```

**本项目怎么做的**
```text
★★ 全部 7 处 fail-fast 都在【启动阶段】:
   空渠道列表 / 默认渠道不存在 / 渠道重名 / 渠道名空白 / base-url 空白 / Redis 连不上 / 配置绑定失败
   ↓
★★ 判据:「★ 这个错误在启动时能不能被发现?能,就必须在启动时发现。」
```

**为什么这比"运行期报 500"好**
```text
★ "启动失败" 是【可发现的事故】→ 部署流程会拦住,日志一眼看到
★★ "请求时才报错" 是【静默的灾难】→ ★★ 探针是绿的,但每个请求都 500
```

**★ 面试话术**

> "我把 7 类配置错误都做成了启动失败。因为**'启动失败'会被部署流程拦住,而'请求时才报错'的探针是绿的** —— 后者可能上线几小时都没人发现。"

## ⚠️ 本项目**没有**用到的常见模式

**知道"为什么不用"比"用过"更难答。**

| 模式 | 为什么本项目不用 |
|---|---|
| **单例** | ★ Spring Bean **默认就是单例** —— ★ 不需要手写 DCL/枚举单例 |
| **建造者(Builder)** | ★ DTO 全是 `record`,★ 字段少,★ 构造器够用 |
| **观察者** | ★ 没有事件驱动的需求;`doFinally` 只是日志钩子,不是订阅机制 |
| **代理(Proxy)** | ★ AOP 场景(事务/缓存)本项目还没有 |
| **熔断器(Circuit Breaker)** | ⚠️ ★★ **确实缺,是真缺口** → [待深入问题](待深入问题.md) |
| **重试(Retry)** | ⚠️ ★★ **故意没做**,理由见 [非流式流程](../02-flows/非流式请求处理流程.md) |
