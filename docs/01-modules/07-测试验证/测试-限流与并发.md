## 一、`RateLimitDecisionTest` —— 只有几行 getter,为什么值得单独测
```java
/**
 * 这里藏着一条【会被写进 HTTP 头、被客户端的重试库照着执行】的换算规则（毫秒 → Retry-After 秒）。
 * 算错 → "调用方按我们说的等，然后又被拒一次"，用户看到一次莫名其妙的重试风暴，还没有任何地方报错。
 * 判据：一段逻辑的输出会被别人依赖着做决定，它就值得一条测试，跟它有多少行代码没关系。
 */
```

```java
// ① 向上取整
assertThat(RateLimitDecision.denied(0, 1399).retryAfterSeconds()).isEqualTo(2);
assertThat(RateLimitDecision.denied(0, 1000).retryAfterSeconds()).isEqualTo(1);  // ★ 整秒不多算
assertThat(RateLimitDecision.denied(0,    1).retryAfterSeconds()).isEqualTo(1);  // ★ 1ms 也报 1 秒

// ② refill = 0 时给保守值,而不是省略这个头
assertThat(RateLimitDecision.denied(0, RateLimitDecision.NEVER_REFILLS).retryAfterSeconds())
        .isEqualTo(60L);

// ③ 三态必须能被区分
// ④ 水位未知 ≠ 水位为零
```
> ★ **向上取整**:1399ms 向下取整会变成 1 秒 → 客户端 1 秒后重试,桶里还差一点,又被拒。Retry-After 的意义是「照着这个数等就一定能过」,向下取整让它变成「照着等也过不去」—— 那这个头还不如不发。
> ★ **为什么 1ms 也报 1 秒**:报 0 秒 = 让客户端"立刻重试" → 桶里本来就没令牌,直接形成重试风暴 —— 这是"限流器把攻击放大成自我 DDoS"的经典形态。

```java
assertThat(decision.retryAfterSeconds())
        .as("省略 Retry-After 的话，标准客户端会用【自己的默认退避】——"
                + "通常比 60 秒激进得多，于是在「等多久都没用」的情况下反复重试。"
                + "给一个明确的、偏保守的数字，比不给强")
        .isEqualTo(60L);
```
> ★★ **规律**:「**"我不知道"比"我不说"好**」—— 省略这个头不是"把决定权交给客户端",而是**把决定权交给了客户端的默认值**,而你不知道那个默认值是多少。

```java
assertThat(RateLimitDecision.allowedWithoutQuota().remaining())
        .as("但必须报「未知」而不是「0」。报 0 是在撒谎（「额度已用尽」），"
                + "会让监控把一次 Redis 故障描述成一次流量高峰 —— 排查方向从一开始就跑偏了")
        .isEqualTo(RateLimitDecision.UNKNOWN_REMAINING)
        .isNegative();
```
> ★★ **规律**:「**错误处理里最贵的 bug,是"用一个合法值表示一个非法状态"**」—— 报 `0` 是合法值,监控分不清"额度用尽"和"限流器坏了",两种完全不同的故障一套排查方向。完整论证 → [类-RateLimitDecision](../06-限流/类-RateLimitDecision.md)

## 二、★★★ `RateLimitConcurrencyTest` —— 整段 G4 存在的理由
```java
/** G4 的验收物（路线图原话）：「并发压测下不超卖，有测试——起 N 个线程同时打，断言放行数严格等于桶容量。」 */
private static final int CAPACITY = 5;
private static final int CONCURRENCY = 32;
```

```java
@Test
void neverOversellsUnderConcurrency() {
    long allowed = countAllowed(limiterWith(CAPACITY, REFILL_DISABLED), "lua");
    System.out.printf("[G4-OBS] LUA impl   : %d concurrent -> bucket capacity %d -> allowed %d%n",
            CONCURRENCY, CAPACITY, allowed);
    assertThat(allowed)
            .as("桶里只有 %d 个令牌，并发下必须【严格】只放行 %d 个。"
                    + "放行多了 = 超卖（钱漏了）；放行少了 = 误杀（可用性掉了）。"
                    + "两个方向都是 bug，所以这里用 isEqualTo 而不是 isLessThanOrEqualTo")
            .isEqualTo(CAPACITY);
}

@Test
void naiveImplementationDoesOversell() {
    long allowed = countAllowedNaive(CAPACITY, REFILL_DISABLED, Duration.ofMillis(20), "naive");
    assertThat(allowed)
            .as("这条断言【必须】是红的（对天真实现而言是绿的）—— "
                    + "如果它不红，说明第一组测试根本没测出并发，第一组的绿也就不值钱了")
            .isGreaterThan(CAPACITY);
}
```
> ★★ **第一条 + 第二条 = 一个被验证过的因果**:只有第一条 → 可能是"这个测试压根测不出超卖",绿了也没意义;只有第二条 → 只是发现一个 bug;两条一起 → "Lua 是拦住超卖的那道墙"。**写测试最值得花时间的地方,就是想清楚"如果这个功能是错的,我的测试会不会红"**。完整展开 → [测试-对照组NaiveTokenBucket](测试-对照组NaiveTokenBucket.md)
> ★ **用 isEqualTo 不用 isLessThanOrEqualTo**:`isLessThanOrEqualTo(5)` 在"只放行 3 个"时也会绿,而"放行少了"同样是 bug(误杀 = 可用性掉了)—— 两个方向都要锁,所以必须用 `isEqualTo`。断言松紧度要匹配业务:两个方向都是 bug 时,不许用单边断言。

```java
/**
 * 本测试要验的恰恰是 Redis 自己的行为：Lua 脚本在 Redis 内部的原子性。
 * mock 掉 Redis = 把唯一要验的东西换成自己写的假货，"我的 mock 说它是原子的"一文不值。
 * 判据：测试替身只能替换"无关的部分"；这里要验的就是 Redis，它不能是替身。
 */
```

```java
/**
 * flatMap 的第二个参数是"最多同时订阅多少个"，不写默认 256——对 32 够用，但写一个刚好等于并发数的值，
 * 让读代码的人一眼看出"这 32 个是同时发出去的"而不是"可能同时"。用 flatMap 不用 concatMap：后者【串行】执行，
 * 串行之下永远不会超卖，测试就变成恒绿的摆设，还特别像在对的东西上做断言。
 */
List<RateLimitDecision> decisions = Flux.range(0, CONCURRENCY)
        .flatMap(i -> limiter.tryAcquire(clientId), CONCURRENCY)
        .collectList()
        .block(Duration.ofSeconds(30));
```
> ★★ **规律**:「**一个恒绿的测试,比没有测试更糟 —— 因为它占据了"这里已经验过了"的位置**」。

```java
@Test
@DisplayName("令牌会回填：容量 2 + 每秒 10 个 → 打光后等 300ms 又能过 1 个")
void tokensAreRefilledOverTime() throws InterruptedException {
    assertThat(drained.retryAfterMillis())
            .as("回填速度 10/s，缺 1 个令牌 → 大约 100ms。"
                    + "这个值会变成 Retry-After 头，所以它必须是个真实的估算而不是拍脑袋的常数")
            .isBetween(1L, 200L);

    Thread.sleep(300);

    assertThat(limiter.tryAcquire(clientId).block().allowed())
            .as("300ms 内按 10/s 回填了 3 个令牌（上限 2），所以必然能过。"
                    + "如果这里还是 false，说明桶根本没回填 —— 那它就不是令牌桶，是个计数器")
            .isTrue();
}
```
> ★★ **证明桶不只是在拒绝**:少了这一条,"限流器"退化成"每个客户端一辈子只能发 capacity 次请求"也能全绿 —— 每个功能都要有一条测试证明它【不只是】在拒绝。
> ★★ **这条抓出过真实 bug**:第一次实现里 ScriptResult 字段叫 `retryAfterMillis`,脚本返回的字段叫 `retryAfterMs` —— 名字对不上,Jackson 静默把 0 留下(不报错、不告警)。抓住它的是「断言一个值落在合理区间」(1~200),不是「断言它不为 null」—— 0 也不为 null,断言不为 null 照样绿。**"断言区间"比"断言非 null"值钱得多**;反面同样重要:**一个字段被静默填成默认值,是 Jackson 最擅长的失败模式**。完整故事 → [类-RedisTokenBucketLimiter-深入](../06-限流/类-RedisTokenBucketLimiter-深入.md)

```java
/** 不回填：桶里就那 CAPACITY 个令牌，测完为止。这样"放行数"才是一个确定的数 */
private static final double REFILL_DISABLED = 0.0;

/** 每个测试用例用独立的桶：共用一个 key 会让测试之间互相消耗额度，红绿随机 */
private static String uniqueClientId(String label) {
    return label + "-" + UUID.randomUUID();
}
```
> ★★ **规律**:「**测试之间共享状态 = 红绿随机**」—— 两条纪律:① 确定性场景把变量钉死(回填关掉);② 需要独立的资源每次新建(随机 clientId)。

## 三、`RateLimitEndToEndTest` —— 429 真的在 HTTP 上
```java
/**
 * 那边验【算法】："并发下放行数严格等于桶容量"（不超卖）；这边验【接线】：
 * "限流真的挂在请求链路上，对外表现是 429 + Retry-After"。两个都要有——算法完全正确但没被调用过，和算法错了，在生产上表现一样：都等于没有限流。
 */
```

```java
// ★★ 本类最重要的一条断言 ★★
//    被限流的请求【压根没到上游】。只断言状态码是不够的 ——
//    一个"先转发、再拒绝"的实现同样返回 429，但它已经把 3 次上游调用变成了 4 次：
//    钱照花，429 只是给用户看的安慰。
UPSTREAM.verify(CAPACITY, postRequestedFor(urlEqualTo("/chat/completions")));
```
> ★★ **规律**:「**每个"防护类"组件都有一条"它拦在了正确的位置吗"的断言**」—— 限流的价值一半在"拒绝",另一半在"拒绝得足够早",`verify(3)` 才是"足够早"的证据。路由的版本是 `verify(0)`(见[路由页](测试-路由与注册表.md)),**一个是"不该发生",一个是"恰好发生 N 次"**。

```java
for (int i = 0; i < CAPACITY; i++) {
    int expectedRemaining = CAPACITY - i - 1;
    webTestClient.post()...
            .expectHeader().valueEquals("X-RateLimit-Limit", String.valueOf(CAPACITY))
            .expectHeader().valueEquals("X-RateLimit-Remaining", String.valueOf(expectedRemaining));
}
```
> ★ **逐次递减比"三个请求都 200"值钱**:只断言 3 次 200,一个"压根没扣减"的实现(每次都报 remaining=3)也全绿;逐次递减锁住了"每次请求真的扣了一个令牌"。

```java
registry.add("gateway.rate-limit.refill-per-second", () -> "0");   // ★ 不回填
...
.expectHeader().valueEquals(HttpHeaders.RETRY_AFTER, "60")
```
> ★★ **为什么是 60 不是 1**:回填关掉 → 脚本返回 `retryAfterMs = -1`(NEVER_REFILLS)→ `retryAfterSeconds()` 走兜底分支 → 60。一个"1"会让你以为等 1 秒就好,实际上等一万秒也没用。

```java
// ---- ★ 刻意【不】覆盖 timeout-millis / fail-open / key-prefix ★ ----
//   Java 字段 timeoutMillis 归一化成 "timeoutmillis"，YAML 当时写的是 timeout-ms，归一化成 "timeoutms"——对不上。
//   ★ 宽松绑定【不会把 ms 展开成 millis】，这个键被整个忽略，long 拿到默认值 0；而同前缀下另外几个键都绑得好好的，现象完全不像"键名问题"。
//   现在这个键由 application.yml 提供，一旦有人改回键名，本测试会因启动自检/参数校验直接变红，而不是悄悄跑着 timeout=0。**让"配置键名写错"有测试能抓住，比在文档里写一句"注意别写错"可靠得多。**
```
> ★★ **规律**:「**"不覆盖某个配置"可以是一种测试设计**」—— 覆盖它 = 绕过生产配置;不覆盖它 = 顺手验了"那份真实的 YAML 绑得上"。

| 测试 | 守什么 |
|---|---|
| `bucketsAreIsolatedPerClient` | ★ **限流维度选得对不对** —— 若所有客户端共用一个桶,"任何一个客户端的 bug 都会把所有人一起限死" |
| `fallsBackToRemoteAddressWhenNoClientId` | ★ **缺 `X-Client-Id` 时退化到来源 IP**,而不是全放行 |

```java
/**
 * ★ 守一个很容易写漏的洞：只在"带了 X-Client-Id"时才限流。那样攻击者只要【不发这个头】就绕过全部限流——一个可以被客户端单方面关掉的防护，等于没有防护。
 *   正确默认："缺少身份标识时按来源 IP 限"，宁可误伤也不能放行。
 */
```
> ★★ **规律**:「**一个可以被客户端单方面关掉的防护,等于没有防护**」—— 判据:这个防护的"开/关"由谁决定?如果是请求方,那它不是防护。

```java
/**
 * ⚠️ 方法名不能叫 post：本类 static import 了 WireMock 的 post(UrlPattern)，而【类内声明的实例方法会遮蔽同名的静态导入】——

 * 起个不会撞的名字，比记住这条规则更划算。

```
> ★★ **规律**:「**起个不会撞的名字,比记住一条语言规则更划算**」—— 和本页其它坑是同一类:报错信息完全不指向真正的原因。

## 四、`RateLimitFailOpenTest` —— 故障路径
```java
/**
 * ★ 为什么这条不能放进端到端测试 ★：RateLimitConfig 的启动自检会拦住"enabled=true 但连不上 Redis"的应用——那种应用【根本起不来】，端到端测试无从谈起。
 * 不是没覆盖到，恰恰相反：启动自检把那类情况提前消灭在启动阶段，于是"运行期 Redis 挂掉"只剩"跑到一半挂掉"这一种可能。
 */
```
> ★★ **规律**:「**"测不到"有时是因为"那一类情况已经被更早的一道防线消灭了"**」—— 判据:是被漏掉了,还是被更早地挡住了?这两个看起来一样,含义完全不同。

```java
/**
 * 拿一个"刚探测到空闲、但没人监听"的端口，把 Lettuce 指过去——连接被立刻拒绝，效果和 Redis 挂掉一样，且不需要 Docker、50 毫秒内跑完。
 * 造故障场景 ≠ "必须起一个真集群"——用最小代价造出等价观测条件，是测试设计的一部分。
 */
private static int findClosedPort() {
    try (ServerSocket socket = new ServerSocket(0)) {
        return socket.getLocalPort();     // ★ 内核分配一个,关掉后短时间没人占用
    }
}
```
> ★★ **规律**:「**"要测故障"不等于"要造一个坏掉的真集群"**」—— 故障的等价条件往往比故障本身便宜得多,这里等价条件只是"这个端口连不上"。

```java
@Test
@DisplayName("fail-open=true（默认）→ Redis 挂了也放行请求，但水位标成「未知」")
void failOpenAllowsRequestWhenRedisIsDown() {
    assertThat(decision.outcome())
            .as("限流器是【保护性】组件，不是【功能性】组件 —— 它的失败不该升级成网关的失败。"
                    + "Redis 抖动 3 秒就拒绝 100% 的请求，是用一次必然发生的全面故障，"
                    + "去防一次可能发生的超卖，这笔账是亏的")
            .isEqualTo(RateLimitDecision.Outcome.ALLOWED);

    assertThat(decision.remaining())
            .as("水位未知时必须报 UNKNOWN(-1)，不能编一个数字。"
                    + "报 0 会让监控显示'额度已用尽'，把一次 Redis 故障描述成一次流量高峰")
            .isEqualTo(RateLimitDecision.UNKNOWN_REMAINING);
}

@Test
@DisplayName("fail-open=false → Redis 挂了就拒绝，而且结果是 UNAVAILABLE（对应 503，不是 429）")
void failClosedRejectsWithDistinctOutcomeWhenRedisIsDown() {
    assertThat(decision.outcome()).isEqualTo(RateLimitDecision.Outcome.UNAVAILABLE);

    // ★★ 这条断言是错误分类纪律的延续，和 G3a 的「400 而不是 502」是同一条 ★★
    //      429 = "你太快了"  → 客户端会退避后重试（而 Redis 挂了，重试一万次也没用）
    //      503 = "我坏了"    → 客户端会换实例/降级，运维会去看我们的服务
    //    共用 429 的后果：客户端做无效重试，值班的人去查"谁在刷接口"。
    //    **错误码选错不只是不好看，是把所有人指错了方向。**
    assertThat(decision.outcome()).isNotEqualTo(RateLimitDecision.Outcome.DENIED);
}
```
> ★★ **两条断言 = 两种降级策略**:fail-open 时放行但水位报「未知」;fail-closed 时拒绝且结果是 `UNAVAILABLE`(503 不是 429)。注意后者的两条断言顺序 —— 先 `isEqualTo(UNAVAILABLE)` 再 `isNotEqualTo(DENIED)`:后者看着"多余",但它表达的是"这个区别是有意的",哪天有人把 UNAVAILABLE 合并进 DENIED,`as(...)` 会告诉他为什么不行。**"错误码选错"和"限流拒绝"在监控上是两种完全不同的告警**。完整的三态对照表 → [流程-一次被限流的请求](../06-限流/流程-一次被限流的请求.md)

> ★★ **规律**:「**流程页可以反过来当"测试覆盖清单"用**」—— 把流程的每个环节列出来逐个问"这个有测试吗",没有测试的环节,就是最可能在重构时被改坏的地方。
