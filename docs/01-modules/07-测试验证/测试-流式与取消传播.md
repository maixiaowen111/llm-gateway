# 测试 · 流式与取消传播

> **本页速览**
> - 流式这条链路要 **4 个测试类、8 个方法**才验得完 —— 本页讲清**为什么是 4 个而不是 1 个**。
> - ★★ 全页最值钱的一句:**「返回 `Flux` ≠ 流式」** —— 中间加一个 `collectList()` 就悄悄变回一次性了,而编译照过。
> - ★ 三个"必须成对"的测试:该杀 / 不该杀、该记 / 不该记、流式真的在流 / 出口真的换了衣服。
> - ★ 取消传播用**日志**当观测点,而不是往生产代码里塞一个测试计数器。
> - ⚠️ 有一个坑和"每块字节数必须相等"有关,和业务毫无关系但会让断言飘。
>

## 为什么流式要 4 个测试类
```text
★ 一个"能拿到回复"的测试,对下面 4 件事全都无感:
   ① 回复是"一块块到的",还是"攒齐了一次性给的"?     → 用户体感差 5 秒
   ② 每块的字段是 OpenAI 协议的,还是上游厂商自己的?   → SDK 解析不了
   ③ 用户中途关页面,上游那条连接到底断没断?          → ★ 每个字都在烧钱
   ④ 上游吐到一半卡住了,网关会等多久?                → ★ 连接永不释放
```
**四个测试类的分工**:

| 测试类 | 验的是 | 一句话 |
|---|---|---|
| `UpstreamStreamingTest` | ★ **"流"本身** | 上游的块是**陆续到的**,不是攒齐再发 |
| `StreamingContractTest` | ★ **出口的形状** | 到客户端的块**换过一身衣服**了 |
| `CancelPropagationTest` | ★ **取消的传递** | 客户端断开 → **上游真被取消** |
| `IdleTimeoutTest` | ★ **停滞的检测** | 中间卡住会被发现,**但健康的长回复不被误杀** |

> ★★ **规律**:「**"能不能用"和"用得对不对"是两个测试**」。★ 流式这条链路上"用得对不对"有 **4 个互相独立**的维度,所以是 4 个类,不是一个类里的 8 个方法(它们的 Spring 上下文和桩都不一样)。
## 一、`UpstreamStreamingTest` —— 流真的在流
### 它在防什么
```java
/**
 * 最容易犯的错:"以为返回 Flux 就叫流式"。某处把整段攒齐再发(加个 collectList()
 * 或对响应做缓冲),返回类型照样是 Flux,编译能过、肉眼看不出,但"打字机效果"就没了。
 */
```
```text
★ "返回 Flux" 和 "元素陆续到达" 是两件事:
   Flux.fromIterable(List.of(1,2,3,4))   ← 类型是 Flux,但元素 ★ 同时全到
★★ 一个 hasSize(4) 的断言,对两种实现 ★ 一视同仁 → 永远绿
```
### 关键技巧:`timestamp()`
```java
List<Tuple2<Long, String>> stamped = client.chatCompletionStreamRaw(request)
        .timestamp()          // ★ 给每个元素盖上"到达时刻"的戳
        .collectList()
        .block();
long spreadMs = stamped.get(EVENT_COUNT - 1).getT1() - stamped.get(0).getT1();
assertThat(spreadMs)
        .as("首尾元素应相隔一段时间（实测滴流 %d ms），说明是真的陆续到达", TOTAL_DRIBBLE_MS)
        .isGreaterThan(TOTAL_DRIBBLE_MS / 3);
```
```text
★★ 加上"首尾相隔 > 400ms" → 攒齐的实现必然红(它的 spread 接近 0)
```
> ★★ **规律**:「**要验"时间上的性质",就得先测出时间**」。`.timestamp()` 是 Reactor 的一行工具,没有它你只能断言"内容对",断言不出"是不是流式"。
### ⚠️ 一个和业务无关的坑
```java
/**
 * withChunkedDribbleDelay 按【字节等分】切响应体,每行必须一样长;不等长,某块会切在
 * 事件中间,解码器要等下一块才敢吐事件,到达时刻就乱了。每个 data: {"n":X}\n\n 恰好 15 字节。
 */
private static final String SSE_BODY =
        "data: {\"n\":1}\n\n" + "data: {\"n\":2}\n\n" + "data: {\"n\":3}\n\n" + "data: {\"n\":4}\n\n";
```
> ★★ **规律**:「**当断言"会飘"时,先怀疑测试工具,再怀疑被测代码**」。★ 同一个坑在本页出现 **3 次**,每个类的注释里都重复解释 —— 不是冗余,读单个测试类的人不会去翻别的类。
## 二、`StreamingContractTest` —— 出口也归一了
### 它和上面那个的关系
```text
★ UpstreamStreamingTest 证明:上游的块 ★ 真的是一块块到的
★ StreamingContractTest 证明:到客户端手里的块 ★ 已经换过一身衣服
★★ 两件事必须分开验 —— 流是真的、但透传了厂商协议,等于白干
```
### 假上游故意埋的两个坑
```java
private static final String REQUESTED_MODEL = "deepseek-chat";
private static final String UPSTREAM_MODEL  = "deepseek-flash";   // ★ 坑 1
private static final String UPSTREAM_OBJECT = "upstream.weird";   // ★ 坑 2
```

| 坑 | 上游报的 | 出口必须是 | 漏掉的后果 |
|---|---|---|---|
| ① `model` | `deepseek-flash` | **`deepseek-chat`** | 客户端看到自己没请求过的模型名 |
| ② `object` | `upstream.weird` | **`chat.completion.chunk`** | OpenAI SDK 认不出这是流式块 |

> ★ 这和 [契约测试页](测试-契约测试.md) 里"故意埋坑"是**同一个手法**:让"不做归一"和"做了归一"的结果不同,断言才有价值。
### ★★ 最漂亮的一条:证明 `[DONE]` 是网关补的
```java
@Test
@DisplayName("上游的 [DONE] 不原样透传，出口的 [DONE] 是网关自己补的")
void doneSentinelIsNotForwardedFromUpstream() {
    // 关键：让上游【不发】[DONE]，只发数据块；出口仍以 [DONE] 收尾 → 网关自己补的。
    UPSTREAM.stubFor(post(urlEqualTo("/chat/completions"))
            .willReturn(aResponse()
                    .withBody(SSE_PREFIX + "\"delta\":{\"content\":\"只有我\"},\"finish_reason\":null}]}\n\n")));
    List<String> events = collectStreamEvents();
    assertThat(doneCount).as("上游没发 [DONE]，出口也应该有且只有一个 —— 说明是网关补的").isEqualTo(1L);
    assertThat(events.get(events.size() - 1)).isEqualTo("[DONE]");
}
```
```text
★★ 要证明"某样东西是我们生成的",就让上游 ★ 不给它 → 出口仍然有 → ★ 只能是网关补的。
★ 对比"看起来也行"的写法:上游给 [DONE] → 出口有 [DONE] → 纯透传下也会绿 → 白写。
```
> ★★ **规律**:「**所有"我们生成了 X"的断言,都必须在一个"输入里没有 X"的场景下做**」。否则你验的是"X 存在",不是"X 是我们造的"。
### 另外两条:delta 字段的分布
```java
assertThat(first.path(...).path("delta").path("role").asText()).isEqualTo("assistant");
assertThat(middle.path(...).path("delta").path("content").asText()).isEqualTo("你好");
assertThat(last.path(...).path("finish_reason").asText()).isEqualTo("stop");
assertThat(middle.path("choices").path(0).path("finish_reason").isNull())
        .as("中间块的 finish_reason 就是显式 null，不能凭空造一个值出来")
        .isTrue();
```
```text
★ 职责分工:role 只在首块 / content 在中块 / finish_reason 只在末块
★★ 而 middle 那条 isNull() 是"负向断言":证明我们 ★ 没有画蛇添足
```
## 三、`CancelPropagationTest` —— 取消真的传下去了
### 它在防什么
```text
★ 如果取消传不下去,网关就是个"漏水的管子":
   用户关了浏览器 → 上游还在吭哧吭哧吐字 → ★★ 每一个字都在烧钱、占着一条连接
★ 单看功能测试("能拿到回复")★ 永远发现不了 —— 它只在"用户中途关掉"时才暴露
```
### ★★ 三级证据链
```java
// ① 先证明流真的在动
CountDownLatch receivedThree = new CountDownLatch(3);
Disposable subscription = responseBody.subscribe(chunk -> receivedThree.countDown());
assertThat(receivedThree.await(15, TimeUnit.SECONDS))
        .as("取消之前必须真的收到至少 3 块，否则'取消成功'什么都证明不了")
        .isTrue();
// ② 真的断开（不是假装断）—— 取消订阅，底层 TCP 连接随之关闭
subscription.dispose();
// ③ 取消必须一路传到上游那条连接上
assertThat(awaitLogMarker(appender, "[cancel]", 15)).isTrue();
```

| 级 | 证明什么 | ★ 少了它会怎样 |
|---|---|---|
| ① | 流**真的在动** | ★ "取消成功"可能只是**压根没东西可取消** |
| ② | 断开的方式是**真断** | ★ 用 `dispose()` 取消订阅 → Netty 关闭 TCP |
| ③ | 信号**穿到了网线** | 穿过 filter / concatMap / timeout 一路到 HTTP 边界 |

> ★★ **规律**:「**"什么都没发生"和"发生了但被正确处理了"看起来一样**」。★ 第 ① 级就是用来把这两者分开的 —— 一个没有前置条件的负向断言,是假绿的重灾区。
### ★★ 观测点为什么是日志,不是计数器
```java
/**
 * 为什么用日志而不是给生产代码加一个"取消计数器":往生产类里塞静态字段或额外 Bean,
 * 是把测试的私货写进产品 —— 上线后它还在那里,没人敢删。而这条 [cancel] 日志本身
 * 就是生产需要的（网关必须知道有多少用户中途放弃），测试只是顺手复用了它。
 */
```
> ★★ **规律**:「**测试要观测生产行为,但不该改造生产代码**」。★ 为了测试加的字段,会在生产里活很久,且没人敢删。
### ★ 负向断言:正常读完不能记成取消
```java
assertThat(hasLogMarker(appender, "[cancel]"))
        .as("正常读完的流绝不能出现取消日志 —— 否则统计出来的'用户中途放弃率'全是假的")
        .isFalse();
assertThat(hasLogMarker(appender, "[stream-end]")).isTrue();
```
> ★ 这条比正向那条**更重要**:如果无脑把每次结束都记成取消,正向照样绿,但日志就彻底失去意义了。
### ★★ 异步断言:用轮询,不用 `sleep`
```java
/**
 * 不能"断开后立刻断言" —— 取消信号要经 Netty channelInactive、Reactor 算子链才落到日志,
 * 是异步的。用轮询而非 sleep 固定时长:既不偶发失败,也不拖慢测试。
 */
private boolean awaitLogMarker(ListAppender<ILoggingEvent> appender, String marker, int timeoutSeconds)
```
> ★★ **规律**:「**异步结果的断言,只有两种写法:轮询,或者偶发失败**」。★ "偶发失败"会被贴 flaky 标签,然后被 `@Disabled` —— 等于删掉。
## 四、`IdleTimeoutTest` —— 停滞被发现,但不误杀
### 它补的是 1d 留下的坑
```text
★ responseTimeout 量的是「请求发出 → 收到响应头」。
   非流式:响应头就是全部内容 → ★ 够用
   流式:响应头几十毫秒就回来,之后内容可能吐几分钟,中途卡死它一点都管不到
★★ 结果:客户端永远等下一个字,网关上留一条 ★ 永不结束的连接
```
### ★★ 两个测试是一对
```java
@Test
@DisplayName("上游中途卡住 → 报 UpstreamIdleTimeoutException，而不是无限等下去")
void stalledUpstreamIsDetected() {
    stubDribbling(8000);   // 8 块摊在 8 秒里 —— 每块间隔约 1000ms，远超 400ms 阈值
    ...
    assertThat(error.get()).isInstanceOf(UpstreamIdleTimeoutException.class);
    assertThat(((UpstreamIdleTimeoutException) error.get()).idleTimeoutMs())
            .as("异常里要带上触发它的阈值，排错时才知道该调哪个配置")
            .isEqualTo(IDLE_TIMEOUT_MS);
}
@Test
@DisplayName("块持续到达时不得误杀 —— 长回复中间停顿几秒是正常的")
void steadyStreamIsNotKilled() {
    stubDribbling(800);    // 8 块摊在 800ms 里 —— 每块间隔约 100ms，远小于阈值
    ...
    assertThat(error.get()).as("块一直在到，空闲超时不该触发").isNull();
    assertThat(received).as("8 块应当一块不少地全部透出去").hasSize(CHUNK_COUNT);
}
```
```text
★★ 只测前者的话,把阈值写成 1 毫秒 ★ 也能过测试 —— 那是个灾难性的配置
★ 后者的失败模式更隐蔽、也更严重:阈值设得跟连接超时一样小(3 秒)
   → 模型思考时正常停顿几秒就被掐断 → ★★ 用户看到"回复说到一半突然没了"
```
> ★★ **规律**:「**一个"防 X 发生"的功能,必须同时测"X 发生了"和"没发生 X 时不许误伤"**」。★ 这个模式在本项目里出现了 **3 次**,是**面试时最值得讲的一条测试方法论**:

| 主题 | 必须发生 | 必须不发生 |
|---|---|---|
| 空闲超时 | 停滞要报错 | ★ **健康长回复不许掐** |
| 取消日志 | 断开要记 `[cancel]` | ★ **正常读完不许记** |
| 限流(见[限流页](测试-限流与并发.md)) | 32 并发不许超卖 | ★ **对照组必须超卖** |
### ★ 为什么不走 HTTP
```java
/**
 * 2c 必须走 HTTP(要真断连);2d 验的是"网关内部判定停滞"。走 HTTP 反而验不准:超时时
 * 响应头早发出去了,状态码改不了,Spring 只能粗暴关连接,客户端收到笼统的"连接被中断",
 * 看不出是空闲超时还是网络抖动。直接在 client 层断言异常类型,验的正是我们写的那行代码。
 */
```
> ★★ **规律**:「**选在哪一层断言,取决于你要区分什么**」。★ 如果在 HTTP 层断言,"空闲超时"和"网络抖动"看起来一模一样 —— 而这个测试的全部意义,就是把它们分开。
### ★ 那条"别扭"的转型是设计在正常工作
```java
// G3b：不能再 @Autowired OpenAiCompatibleProvider 了 —— 渠道不是 Bean
this.client = (OpenAiCompatibleProvider) providerRegistry.resolve("deepseek");
/**
 * "不得不转型"的别扭是设计在正常工作:它标示出 SPI 边界 —— 注册表给的是"渠道"抽象,
 * "上游原始行长什么样"是抽象之外的东西,想碰就得自担风险。
 */
```
> ★★ **规律**:「**"用起来别扭"有时是边界在正确地挡你**」。★ 如果别扭的地方恰好是"我不该碰的东西",那它是保护,不是缺陷。

## 容易卡住的点
### 卡点 1:⚠️ `withChunkedDribbleDelay` 在字节边界上切
```text
★ 它按字节等分,不是按 SSE 事件等分 → 每块内容长度必须严格相同
   → 否则某块切在事件中间,解码器要等下一块,到达节奏就乱了
★ 本页 3 个类都撞过这个坑,注释里都写了
```
### 卡点 2:★ 测试里所有上游内容都用 ASCII
```java
/**
 * 用 ASCII 而非中文:Windows/Git Bash 下中文会被编成 GBK,断言消息乱码就没法读。
 * 这个项目已在这个坑上栽过两次。
 */
private static final String DS_CONTENT = "from-deepseek";
```
> ★ 这和 M1 里 `loadScript()` 必须显式 `StandardCharsets.UTF_8` 是**同一个根因**(JDK 17 在中文 Windows 上默认 GBK)→ 见 [类-RedisTokenBucketLimiter-深入](../06-限流/类-RedisTokenBucketLimiter-深入.md)。
### 卡点 3:★ `[cancel]` 日志的 appender 会收到**所有渠道**的日志
```java
/**
 * 日志按【类】挂,而 OpenAiCompatibleProvider 服务所有渠道,所以 3b 在 [cancel]/[stream-end]
 * 里加了 channel= —— 多家渠道并存后,"哪个渠道的用户最没耐心"是个真问题。
 */
```
> ★★ **规律**:「**G3b 把"一个实现类 × N 份配置"引入之后,按类挂的观测点就变得"过宽"了**」。★ 解法是在**日志内容里带上维度**(`channel=`),让观测点保持粗粒度,把维度信息放进数据里。
### 卡点 4:★ 上游必须"吐得够慢",否则测不了取消
```java
/**
 * 必须"吐得够慢":上游一瞬间吐完,还没等到 3 块整条流就正常结束了,那时再 dispose
 * 流已完成,取消无从谈起。要验取消,就得让上游一直活着。
 */
private static final int UPSTREAM_CHUNK_COUNT = 20;
private static final int TOTAL_DRIBBLE_MS = 8000;
```
