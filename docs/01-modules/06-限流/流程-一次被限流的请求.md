# 流程 · 一次被限流的请求

> **本页速览**
> - 端到端走一遍:**从 curl 发出,到客户端拿到 `429`**,中间经过 6 个环节。
> - ★ 关键观察:**请求在 filter 里就被拦下了,`ChatController` ★ 一行代码都没执行**。
> - ★★ 本页重点讲**桶里令牌数是怎么变的** —— 这是唯一"看不见但决定一切"的状态。
> - ★ 三种拒绝形态(429 / 503 / fail-open 放行)用同一张图对照。
> - ✅ 结尾附**测试覆盖清单**:哪些环节有端到端测试、哪些只验到决策层。

## 触发条件
**要触发限流,需要同时满足四个条件**:
```text
① gateway.rate-limit.enabled = true        ← 总开关
② 请求路径在 PROTECTED_PATHS 里            ← 目前只有 /v1/chat/completions
③ 同一个 clientId 的桶里令牌不够
④ （如果是 UNAVAILABLE)Redis 不可用 + fail-open = false
```
**配置演示**:
```yaml
gateway:
  rate-limit:
    enabled: true
    capacity: 3              # ★ 桶容量 3 —— 便于观察
    refill-per-second: 1     # ★ 每秒补 1 个
    fail-open: true
    timeout-millis: 200
    key-prefix: gw:rl
```
**复现命令**:
```bash
for i in 1 2 3 4 5; do
  curl -s -o /dev/null -w "第 $i 次: %{http_code}  " \
    -X POST http://localhost:8081/v1/chat/completions \
    -H "Content-Type: application/json" \
    -H "X-Client-Id: demo" \
    -d '{"messages":[{"role":"user","content":"hi"}]}'
done
```
```text
第 1 次: 200  第 2 次: 200  第 3 次: 200  第 4 次: 429  第 5 次: 429
```
> ★ **注意 `X-Client-Id: demo`** —— 有这个头,5 次请求共用一个桶;不带头 clientId 退化成来源 IP,效果一样(本机)。

## ★ 先把"桶"的状态变化列出来

| 时刻 | 请求 | 桶内令牌(请求前 → 请求后) | 结果 | `Retry-After` |
|---|---|---|---|---|
| T+0.0s | 第 1 次 | **3.0 → 2.0** | ✅ 200 | —— |
| T+0.1s | 第 2 次 | **2.0 → 1.0** | ✅ 200 | —— |
| T+0.2s | 第 3 次 | **1.0 → 0.0** | ✅ 200 | —— |
| T+0.3s | 第 4 次 | **0.0**(补了 0.0)→ 0.0 | ❌ **429** | **1** |
| T+0.4s | 第 5 次 | **0.1**(补了 0.1)→ 0.0 | ❌ **429** | **1** |

```text
① ★ 前三次是"满桶开始" —— 首次访问 tokens = capacity(见 Lua 脚本)
② ★ 第 4 次"补了 0.0":距上次结算仅 0.1 秒,1/s 的速率补不到 1 个
③ ★★ 第 4/5 次被拒,但桶状态照样被写回(值没变)→ Lua 注释"放行与否都写"的现场
```
## 步骤化讲解
### 第 ①步:filter 的两个快速判断
```java
if (!properties.enabled() || !isProtected(exchange)) {
    return chain.filter(exchange);
}
```
```text
enabled = true → 继续;isProtected("/v1/chat/completions") → 在 PROTECTED_PATHS 里 → ★ 继续
```
> ★ **这一步不碰 Redis、不碰网络,纯内存判断** —— 对不在白名单的请求(`/ping`),限流开销是**零**。
### 第 ②步:解析 clientId
```java
String clientId = resolveClientId(exchange);
// 请求带了 X-Client-Id: demo → ★ 返回 "demo"
```
**→ `key = "gw:rl" + ":" + "demo" = "gw:rl:demo"`**
> ⚠️ 不带头会退化成来源 IP `"127.0.0.1"`;本机两种效果一样,但在 nginx 环境里差别巨大 → [深入页](类-RateLimitWebFilter-深入.md)
### 第 ③步:`tryAcquire("demo")` —— 进 Lua 脚本
**这是整条流程的核心。把 Lua 五个步骤对着第 4 次请求走一遍。**
#### ① 读:桶已存在
```lua
local state  = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
-- → {"0", "1750000000200"}   ← 上次结算后是 0,时间是 T+0.2s
local tokens = tonumber(state[1])   -- 0
local ts     = tonumber(state[2])   -- 上次结算时刻
```
#### ② 补:惰性回填,这次补了 0.0
```lua
local elapsed = now - ts            -- 0.1 秒 = 100ms
tokens = math.min(3, 0 + 100 * 0.001)   -- ★ 0 + 0.1 = 0.1
```
```text
★ refillPerMs = 1 / 1000 = 0.001 → 100ms 间隔 × 0.001 = ★ 0.1 个令牌 → 还是不够 1 个
```
> ★★ **容易忽略的点**:桶里令牌是 **小数**(0.1),不是整数;`remaining` 返回前才 `math.floor` 成整数(报 0)。**内部保留精度,对外报整数** —— 否则每 0.1 秒的补充会被反复丢掉。
#### ③④ 判断 + 扣减:不够,算 `retryAfterMs`
```lua
requested = 1
tokens    = 0.1
-- 0.1 >= 1 ? 否
retryAfterMs = math.ceil((1 - 0.1) / 0.001)
             = math.ceil(0.9 / 0.001)
             = math.ceil(900)
             = ★ 900ms
```
```text
★ 900ms 含义:"再等 900 毫秒,就够 1 个令牌了" → 会一路传到 HTTP 头
```
#### ⑤ 写回
```lua
redis.call('HSET', KEYS[1], 'tokens', 0.1, 'ts', now)
-- ★ 被拒了,但仍然写回
```
> ★★ **注释里的理由**:*"被拒时如果故意不写,下次请求会拿旧的 `ts` 重算 —— 结果虽然一样,但桶状态不再代表'此刻的真实水位',`hgetall` 看不出任何东西。可观测性不是加个日志就有的,是让状态本身可读。"*
**这条的现场价值**:随时用一行命令看"这个客户端还剩多少":
```bash
redis-cli hgetall gw:rl:demo
# 1) "tokens"   2) "0.1"
# 3) "ts"       4) "1750000000300"
```
#### 返回
```json
{"allowed":0, "remaining":0, "retryAfterMs":900}
```
### 第 ④步:反序列化 + 转换成 Decision
```java
ScriptResult result = objectMapper.readValue(json, ScriptResult.class);
// ★ 装箱类型 + 构造器判空 → 缺字段会在这里炸
return RateLimitDecision.denied(0, 900);
//                                ↑ remaining  ↑ retryAfterMillis
```
### 第 ⑤步:三态分支 → `DENIED`
```java
case DENIED -> {
    headers.set(HttpHeaders.RETRY_AFTER, String.valueOf(decision.retryAfterSeconds()));
    //                                      ★ 900ms → (900 + 999) / 1000 = 1 秒
    log.warn("[限流-拒绝] client={}，剩余={}，建议 {}s 后重试（容量 {}，回填 {}/s）",
            "demo", 0, 1, 3, 1.0);
    yield writeError(exchange, HttpStatus.TOO_MANY_REQUESTS,
            "rate_limit_error", "rate_limit_exceeded",
            "请求过于频繁，请 1 秒后重试");
}
```
**★ 注意 `900ms → 1 秒`**:`retryAfterSeconds() = (900 + 999) / 1000 = 1899 / 1000 = ★ 1`(整数除法)→ **向上取整:900ms 要等 1 秒,不是 0 秒**;否则客户端会"立刻重试" → 又不够 → ★ 重试风暴。
> ★ 这条和 [类-RateLimitDecision](类-RateLimitDecision.md) 里"`Retry-After` 是承诺不是估算"是同一件事。
### 第 ⑥步:客户端收到什么
```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/json
X-RateLimit-Limit: 3
X-RateLimit-Remaining: 0
Retry-After: 1

{
  "error": {
    "type": "rate_limit_error", "code": "rate_limit_exceeded",
    "message": "请求过于频繁，请 1 秒后重试"
  }
}
```
> ★ **`X-RateLimit-Limit` 和 `Remaining` 在分支之前就设了** —— 所以**连 429 响应里也有完整配额信息**,客户端能算出"离限额还有多远",不用等被拒。

## 时序图
```mermaid
sequenceDiagram
    autonumber
    participant C as 客户端
    participant F as RateLimitWebFilter
    participant L as Limiter
    participant R as Redis
    participant CC as ChatController

    C->>F: POST /v1/chat/completions<br/>X-Client-Id: demo
    F->>F: enabled? ✅ isProtected? ✅
    F->>F: resolveClientId → "demo"
    F->>L: tryAcquire("demo")
    L->>R: EVALSHA &lt;sha1&gt; gw:rl:demo 3 1.0 1
    R->>R: ★ TIME / HMGET / 补 0.1 / 判断 / HSET
    R-->>L: {"allowed":0,"remaining":0,"retryAfterMs":900}
    L->>L: parseDecision → denied(0, 900)
    L-->>F: RateLimitDecision
    F->>F: Retry-After = retryAfterSeconds() = 1
    F->>F: log.warn("[限流-拒绝] ...")
    F-->>C: 429 + X-RateLimit-* + Retry-After + 错误体
    Note over CC: ★ 一行代码都没执行
```
```text
★ 最后那个 Note:ChatController ★ 完全没参与
   → 路由匹配没做 / JSON 反序列化没做 / ChatController 日志没打 → ★★ "限流是最便宜的一道闸"
```
## ★ 三种拒绝形态的对照
```text
【形态 A:DENIED(429)】← 本页主讲
   桶不够 → 429 + Retry-After + X-RateLimit-*
【形态 B:UNAVAILABLE(503)】← fail-open = false + Redis 挂
   tryAcquire 抛异常 → onLimiterFailure → unavailable()
   → ★ 503 + server_error + rate_limiter_unavailable
   → ★ 没有 Retry-After(等多久都没用,是我们在修)
【形态 C:fail-open 放行】← fail-open = true + Redis 挂
   tryAcquire 抛异常 → onLimiterFailure → allowedWithoutQuota()
   → ★ 200 正常服务
   → ★★ 但发 ERROR 日志:"说明网关当前没有任何额度防线"
   → ⚠️ 而且 ★ 不发 X-RateLimit-Remaining(因为 remaining = -1)
```

| | A · DENIED | B · UNAVAILABLE | C · fail-open |
|---|---|---|---|
| 触发 | 桶里不够 | Redis 挂 + fail-closed | Redis 挂 + fail-open |
| 状态码 | **429** | **503** | **200** |
| `Retry-After` | ✅ 有 | ❌ 无 | ❌ 无 |
| `X-RateLimit-Remaining` | ✅ `0` | ❌ 不发 | ❌ ★ 不发(`-1`) |
| 日志级别 | `warn` | ★ **`error`** | ★ **`error`** |
| 客户端该做 | 退避后重试 | ★ **等,别重试** | 正常处理 |

> ★★ **规律**:「**同一个组件有三种"拒绝形态",区别全在"客户端该做什么"**」。★ 这张表可直接当**测试用例清单** —— 三种形态各写一条。

## 容易卡住的点
### 卡点 1:★ 本地测不出"桶在补",因为补得太慢
```bash
# 连续打 5 次 → 第 4、5 次 429 ✅;等 1 秒再打 → ★ 还是 429?
```
```text
capacity=3, refillPerSecond=1 → 被拒时桶里是 0,每秒才补 1 个 → 等 1 秒补到 1.0 → ★ 刚好够,应该能过
   ↓ ★ 但如果你等 0.9 秒:补到 0.9 → 不够 → 还是 429,Retry-After 会告诉你要等 1 秒
```
**怎么办**:照 `Retry-After` 的值等,或把 `refill-per-second` 调大(比如 10)便于观察。
> ★ 这条坑本身有正面价值:**它证明了"补"是真的在算**,不是拍脑袋。
### 卡点 2:★ 用同一个 clientId 测,却测出了意外的结果
```text
★ "同一个 clientId 共用一个桶"是 ★ 设计目标,不是 bug
   → 但若你在别的终端也用了 X-Client-Id: demo → 你在跟"另一个终端"共用额度 → ★ 排查:redis-cli hgetall gw:rl:demo
```
> ★ **规律**:「**有共享状态的地方,测试前先看一眼那个状态**」。本项目运气好:桶状态 `hgetall` 一眼可读 —— 正是 Lua"放行与否都写"带来的好处。
### 卡点 3:⚠️ 不带 `X-Client-Id` 时,你以为在测"一个人",其实在测"一个 IP"
```text
本机测试:remoteAddress = 127.0.0.1 → clientId = "127.0.0.1" → ★ 所有不带头发的请求共用一个桶
   ↓ ★ 本机无所谓,但:同机的 curl 和浏览器 ★ 会互相挤;★★ 上了生产 + nginx → 全员共用一个桶 → 全员限死
```
> ⚠️ 这条在 [深入页](类-RateLimitWebFilter-深入.md) 有完整交代;**本机测试养成"总带 `X-Client-Id`"的习惯**,能提前暴露问题。
### 卡点 4:★ `Retry-After: 1` 但明明 0.9 秒就够了
```text
★ 这是 ★ 有意的:向上取整 900ms → 1 秒
   ↓ ★ 为什么不给"更精确"的值?因为 HTTP 头只有 ★ 秒 这个粒度 → ★ 宁可多等 0.1 秒,也不要"照着等还过不去"
```
> ★ 见 [类-RateLimitDecision](类-RateLimitDecision.md) 的 `retryAfterSeconds()`。

```text
★★ 为什么 503 那条【只验到决策层】不算真缺口?

   ★★ 而"跑到一半"正适合用 FailOpenTest 那种直接构造组件的方式测 ——
     ★ 这是【测不了】,不是【没测】,区别值得说清楚。
```
