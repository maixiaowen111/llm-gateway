### 两处"故意的错位"(别被绕晕)

1. **`RateLimitConfig` / `RateLimitProperties` 在 `config` 包里,但文档归到 M6 限流。**
   因为它们讲的是"限流怎么装配",不是"通用的配置机制"。
2. **`ProviderConfig` / `ProviderProperties` 同样在 `config` 包里,但文档归到 M2。**
   同理 —— 它们只服务于渠道抽象这一件事。

> **规律**:一个类属于哪个模块,看**它为什么存在**,不看它放在哪个文件夹。

## 四、三条主线流程

读代码最容易迷路的地方是"从哪进、到哪出"。这三条是主干:

```text
① 应用启动
   main() → 配置绑定 → ProviderConfig 造注册表(fail-fast)
                      → RateLimitConfig 自检 ping Redis
   → 详看:02-flows/启动流程

② 非流式请求
   POST /v1/chat/completions
   → RateLimitWebFilter(判定) → ChatController → ProviderRegistry(选渠道)
   → OpenAiCompatibleProvider → WebClient → 上游
   → 出错:UpstreamExceptionHandler 转成 OpenAI 格式
   → 详看:02-flows/非流式请求处理流程

③ 流式请求
   同 ②,但出口是 Flux,且取消传播 / 逐块空闲超时是重点
   → 详看:02-flows/流式请求处理流程
```

## 五、代码里的三条"铁律"

后面每一页都会反复用到这三条,先把它们记住:

1. **厂商差异只能存在于 `provider/` 包里。**
   自检方法:在 `ChatController.java` 里搜 `DeepSeek`,**零结果**才算合格。

2. **成功和失败的响应必须是一套格式。**
   成功是 OpenAI 格式、失败是 Spring 默认的白板页 —— 那等于没有契约。

3. **WebFlux 的请求挂在事件循环上,不是挂在一条线程上。**
   所以任何**阻塞调用**(同步 IO、`Thread.sleep`、阻塞版 Redis)都会拖垮
   整个事件循环覆盖的所有连接。这不是"慢一点",是"架构被破坏"。
