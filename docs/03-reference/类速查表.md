# 类速查表

> **本页速览**
> - 项目一共 **21 个主类、2284 行代码**,全部列在这一页,每行都链到它的详解页。
> - ★ 三种用法:**按包找**(知道自己在哪个模块)、**按行数找**(看哪些是重头戏)、**倒排找**(知道要改什么,反查去哪个类)。

**这张表是这一页最省时间的地方。**

|---|---|---|

| 改**路由规则本身** | `ProviderRegistry#resolveOrDefault` | ★ 三种输入的分支在这 |
| 让上游的**新字段也能出网** | `OpenAiCompatibleProvider#normalize` | ★★ 归一 = 网关的护城河 |
| 让**流式多一种协议尾巴** | `ChatController#streamToClient` | ★ `[DONE]` 属于网关承诺 |
| 改**错误响应长什么样** | `UpstreamExceptionHandler` + `OpenAiErrorResponse` | ★ 一个地方改,全部生效 |
| 加**新的状态码映射** | `UpstreamExceptionHandler` | ⚠️ 流式已开始后**映射不了** |
| 改**限流开关 / 额度 / 回填速率** | `application.yml` 的 `rate-limit` 段 | ★ 全部有默认值 |
| 改**限流判定算法** | `RedisTokenBucketLimiter` + `scripts/token_bucket.lua` | ★★ 改 Lua 才动得了原子性 |
| 改**哪个路径要限流** | `RateLimitWebFilter` 的 `PROTECTED_PATHS` | ★ `/ping` 必须不在里面 |
| 改**怎么识别一个客户端** | `RateLimitWebFilter#resolveClientId` | ★ `X-Client-Id` 优先,回落远端 IP |
| 加**新端点** | `ChatController` 或新建 Controller | ★ 新 Controller 默认**不受限流保护** |

## ★ 容易混淆的类对

### ① `ProviderProperties` vs `ProviderConfig` vs `ProviderRegistry`

```text
ProviderProperties  → ★ 配置的【形状】。只有字段,没有逻辑,不认识 Provider
ProviderConfig      → ★ 装配。把 N 份配置【造成】N 个 Provider 对象,装进注册表
ProviderRegistry    → ★ 路由。拿着已经造好的对象,回答"这个名字对应谁"
```

```text
★★ 一句话区分:【描述配置】/【造对象】/【用对象】
   ★ 三者的失败模式完全不同:
     · Properties 错 → 配置读不出来(启动就炸)
     · Config   错 → ★★ 对象造错了,而注册表一切断言都对(最阴险)
     · Registry 错 → 路由错,但至少能测出来
```

> ★ 见 [测试-路由与注册表](../01-modules/07-测试验证/测试-路由与注册表.md) 的分工图。

### ② 限流那 5 个

| 类 | 层次 | 一句话 |
|---|---|---|
| `RateLimitProperties` | 配置 | **数值是多少** |
| `RateLimitConfig` | 装配 | **要不要装**(开关 + 启动自检) |
| `RateLimitWebFilter` | 链路 | **什么时候判、判完怎么回**(三态分支 + 响应头) |
| `RedisTokenBucketLimiter` | 算法 | **怎么判**(Lua 原子) |
| `RateLimitDecision` | 结果 | **判出来是什么**(三态 + Retry-After) |

```text
★★ 分层的收益:想换算法(计数器/滑动窗口)★ 只动 Limiter,
   filter / properties / decision 全都不用改
```

### ③ `ChatCompletionResponse` vs `ChatCompletionChunk`

```text
★ 非流式:【一整份】响应 —— 一次给完,缺字段就没法给
★ 流式  :【一片】响应 —— 缺字段是【正常】的(role 只第一片有)
★★ 所以两者的字段处理策略【故意不同】:前者填默认值,后者不填
```

### ④ `UnknownProviderException` vs `UpstreamIdleTimeoutException`

| | 谁的错 | 出口 |
|---|---|---|
| `UnknownProviderException` | ★ **客户端**(拼错了渠道名) | **400**,且上游一次都没被调 |
| `UpstreamIdleTimeoutException` | ★ 上游慢 | ⚠️ **没有状态码** —— 响应头早发出去了 |

> ★ 见 [M5 错误处理](../01-modules/05-错误处理/_index.md)。

### ⑤ 两个"超时"归属不同

```text
WebClientConfig 里的 2 个 → ★ 传输层,挂在共用 HttpClient 上,所有渠道共享
Provider 里的 1 个        → ★ 业务判断,"多久算卡住"每个渠道可以不同
```
