# FAQ

> **本页速览**
> - 按 **你看到的现象** 组织,不按技术分类 —— ★ 排障时你手上只有"现象"。
> - ★ 每条都是同一个结构:**现象 → 原因 → 怎么办**,★ 先看"原因"再动手。
> - ★★ 最高频的三条:启动报"渠道不存在"、请求返回 **502**、**流式不生效**。
> - ⚠️ 有一条**不是故障**:api-key 没配**不会**导致启动失败,只会在请求时报 502 —— 这是**故意的**。

## A. 启动失败(★ 这一类**全都是故意的**)

### A1. 报"没有任何渠道"/ 一个渠道都没有

```text
★★ 原因:gateway.providers.channels 是空的 —— ★ 一个不路由任何东西的网关没有存在意义
★ 怎么办:检查 application.yml 里 channels 下面有没有缩进正确的渠道段
   ★ 判据:channels 下面必须至少有一个带 base-url 的键
```

### A2. 报"`xxx` 不存在,可用的有:`deepseek, moonshot`"

```text
★★ 原因:default-channel 或者请求里的 provider 写了一个没注册的名字
★ 怎么办:★ 直接照着错误信息里"可用的有"改 —— ★ 那条信息就是为此写的
   ★ 见 类-ProviderRegistry
```

### A3. 报 base-url 是空白

```text
★ 原因:某个渠道漏了 base-url,或者环境变量没传进来
★ 怎么办:① 检查 yml 该行有没有写 ② 检查对应的环境变量(GATEWAY_*/厂商变量)有没有注入
★★ 注意:base-url 空白是 fail-fast 的,★ 而 api-key 空白不是 —— 见 A4
```

### A4. ★⚠️ 没配 api-key,**启动却成功了**

```text
★★ 这不是 bug,是刻意的:
   · base-url 空白 → ★ 启动就炸(它决定了"打到哪",错了一定是配置事故)
   · api-key 空白 → ★ 只打一条 warn(它是【秘密】,本地开发/跑测试时经常没有)
   ↓
★ 表现:启动正常,但 ★ 请求会 502(上游回 401,网关翻译成 502)
★ 怎么办:配上厂商的 key。★ 见 D1
```

### A5. 启动报 Redis 连不上

```text
★ 原因:rate-limit.enabled=true,但限流配置里做的启动自检连不上 Redis
★★ 这正是自检的价值:★ 把"限流静默失效"变成一个响亮的启动失败
★ 怎么办:① 确认 Redis 起了 ② 确认端口对
   ⚠️ ③ 确认前缀是 spring.data.redis.*(Boot 3),不是 spring.redis.*(Boot 2)
      ★ 前缀写错不会报"前缀错",表现就是连不上
```

### A6. 启动报配置绑定失败

```text
★ 原因:YAML 里的键名和 Java 字段对不上
★★ 最经典的一个:YAML 写 timeout-ms,Java 字段叫 timeoutMillis
   宽松绑定把两边归一成 "timeoutms" vs "timeoutmillis" → ★★ 对不上
   ★★★ 而绑定失败【不会报错】,只会静默用默认值(0)——
       除非配了 ignoreUnknownFields = false
★ 怎么办:★ 加 ignoreUnknownFields=false,让它报错而不是静默 ——
   ★ 见 启动流程 的"宽松绑定陷阱"
```

### A7. 端口被占用

```text
★ 默认 8081(server.port)。★ 被占用 → 换端口或杀掉占用进程
```

## B. 请求返回错误

### ★★ B1. 返回 **502 `upstream_unreachable`**

```text
★ 含义:网关【连不上上游】—— DNS 解析不了、端口不通、TLS 失败
★ 怎么办:
   ① 看日志里那条 [上游原始响应] / 连接异常,★ 里面有 channel= 和 base-url
   ② ★★ 最常见的是 ★ api-key 没配 或 配错了 → 上游回 401 → 网关翻译成 502
      (★ 502 而不是 401,因为"上游拒绝了我们"是【网关的问题】,不是客户端的)
   ③ 检查 base-url 结尾:★ /v1 归 base-url 管,/chat/completions 归代码管
```

### B2. 返回 **504 `upstream_read_timeout`**

```text
★ 含义:★ 上游在 read-timeout(默认 30s)内 ★ 连响应头都没给
★ 怎么办:① 上游确实慢 → 调大 gateway.upstream.read-timeout-ms
         ② 网络/代理问题 → 检查本机网络
```

### B3. 返回 **504 `upstream_connect_timeout`**

```text
★ 含义:★ 连接都建不起来(默认 3s)
★ 怎么办:★ 通常不是"上游慢",而是 ★ 地址错了 / 被防火墙挡了 / 代理没配
```

### ★★ B4. 返回 **400 `unknown_provider`**

```text
★ 含义:请求里的 provider 字段写了一个不存在的渠道名
★★ 注意:这时 ★ 上游一次都没被调 —— ★ 400 是唯一"客户端自己错"的状态码
★ 怎么办:★ 改 provider 的值,或去掉这个字段(会用默认渠道)
   ⚠️ ★ 本项目【不会】静默回落到默认渠道 —— 那是刻意的设计
```

### B5. 返回 **429**

```text
★ 含义:★ 你被限流了(桶空了),看 Retry-After 头是几秒
★ 怎么办:① 退避重试 ② 调大 capacity / refill-per-second
   ★ 判据:响应里有 X-RateLimit-Limit / Remaining → ★ 说明限流真的生效了
```

### B6. 返回 **503**

```text
★★ 含义:★ 限流器自己坏了(Redis 连不上),而且配置成了 fail-closed
   ★ 和 429 完全不同:429 是"你太快",503 是"我坏了"
★ 怎么办:★ 查 Redis —— ★ 重试没用,这时候该看运维告警
   ★ 默认配置是 fail-open=true,所以正常情况下你会看到"放行且 Remaining 未知"
```

### B7. 收到 200,但内容不对

```text
★ 检查是不是 ★ 上游偷偷换了模型:
   ★ 本项目出口的 model 报的是 ★ 你请求的那个,不是上游回报的那个
   ★★ 所以"看起来对"不一定代表上游真的用了你要的模型 —— ★ 去日志里看 [上游原始响应]
```

## C. ★★ 流式相关(最高频)

### ★★ C1. 流式"不生效" —— 一次性返回全部内容

```text
★★ 先排除客户端:★ curl 必须加 -N,否则看不到边收边显
★ 还是不行 → 看这几处:
   ① 请求体里 stream 是不是真的是 true(★ 不是字符串 "true")
   ② ★★ 中间有没有人写了 collectList() / block()
      ★ 这会让流【悄悄】退回批处理 —— ★ 编译通过、日志全对、就是不流式
   ↓
★★ 唯一可靠的判据:★ 量"第一块到达的时间"和"最后一块的时间"差多少
   ★ 一样 → 它是批处理
   ★ 见 测试-契约测试 的 .timestamp() 做法
```

### C2. 流式中途断了

```text
★ 逐个排除:
   ① ★ 空闲超时:上游两个块之间超过 idle-timeout-ms(默认 20s)
      ★ 日志里会有空闲超时异常
   ② ★ 客户端自己断的 → 日志里是 [cancel] 而不是 [stream-end]
   ③ ⚠️ ★ 流式开始后【不能再改状态码】—— 所以断了就是断了,不会有 504
```

### C3. ★ 日志里 `[cancel]` 和 `[stream-end]` 分不清

```text
★ [stream-end] → ★ 正常读完,上游连接已释放
★ [cancel]     → ★★ 客户端断开了,已通知上游停止 —— ★ 这一行帮你确认"钱不再烧了"
★ 两者都没有 → ★ 流既没读完也没被取消 → ★ 检查空闲超时
```

### C4. 流式输出里有两条 `data: [DONE]`

```text
★★ 不该发生 —— [DONE] 只补一次,在 ChatController#streamToClient
★ 如果真出现两条:★ 说明上游的 [DONE] 没被 filter 掉
   ★ 正常情况下 filter 会丢它,★ 所以更可能是有第二处在补
```

## D. 配置与安全

### ★ D1. api-key 应该写在哪?

```text
★★ 铁律:★ 绝不写进 application.yml 的值里,绝不进 Git
★ 正确写法:
   application.yml →  api-key: ${DEEPSEEK_API_KEY:}     ← ★ 冒号后留空
   运行时          →  export DEEPSEEK_API_KEY=sk-xxx
   ↓
★★ 冒号后面留空是关键:★ 这样"没配"是一个【可发现的状态】(warn 日志),
   ★ 而不是一个硬编码的秘密 ★ 被 commit 进仓库
```

### D2. 加一家新厂商要改什么?

```text
★★ 答案:★ 只改 application.yml 的 channels 段,Java 一行不动
   ★ 前提是那家厂商的接口和 OpenAI 兼容 —— ★ 这正是"一个实现 × N 份配置"
   ⚠️ 如果那家厂商的请求/响应结构不一样 → ★ 才需要新写一个 Provider 实现
      ★★ 而那时改动会被关在【那一个类】里 —— Controller 和 DTO 一行不动
```

### D3. 改了配置不生效

```text
★ 检查:
   ① ★ 键名有没有写错(见 A6 的宽松绑定陷阱)
   ② ★ 环境变量是不是覆盖了 yml 里的值 —— ★ ${ENV:default} 的语义是"环境变量优先"
   ③ 改完有没有重启
```

## E. 测试相关

### ★★ E1. Testcontainers 报 Docker API 400

```text
★ 现象:起 redis:7 容器时报 400 Bad Request / 版本不兼容
★ 原因:★ Docker 客户端和服务端 API 版本协商不上
★ 怎么办:★ 设 DOCKER_API_VERSION=1.44 再跑
```

### E2. 测试里中文乱码 / 字节数对不上

```text
★★ 原因:★ JDK 17 在中文 Windows 上默认字符集是 GBK(JDK 18 才改成 UTF-8)
★ 怎么办:
   ① 所有显式编码的地方用 StandardCharsets.UTF_8,★ 不要依赖默认值
   ② ★ 假上游返回的测试内容 ★ 保持纯 ASCII —— ★ 这样"字节数"才是确定的
   ⚠️ 这条和 WireMock 的 withChunkedDribbleDelay 有关:★ 它按【字节】切,
      ★ 所以每个分片必须等长,中文会让字节数不可预测
```

### E3. 测试偶发失败(时快时慢)

```text
★ 常见的两类:
   ① ★ 依赖真实时间(比如"令牌回填")→ ★ 用轮询等待,而不是 sleep
   ② ★ 竞态窗口太小,偶尔才出现 → ★ 放大窗口,★ 把偶发变必然
★ 判据:★ 一条会自己变红的测试,迟早会被团队关掉 —— ★ 那等于没测
```

### E4. 单元测试全绿,但应用跑起来是坏的

```text
★★ 这不是意外,是常态 —— ★ "零件合格" ≠ "整机合格"
★ 最典型的:ProviderConfig 装配写错了(比如所有渠道共用一个 base-url)
   → ★ 注册表收到了错的对象,它的一切断言【都对】
   → ★★ 只有端到端测试能发现
★ 怎么办:★ 给"装配"这一步单独写测试
```

## F. 其他

### F1. `/ping` 为什么不被限流?

```text
★★ 因为探针必须能绕开业务链路 ——
   ★ 如果健康检查也被限流打回 429,★ 编排系统会以为你的服务挂了,然后把它重启
   ★ 见 RateLimitWebFilter 的 PROTECTED_PATHS
```

### F2. 日志里 `[上游原始响应]` 会不会泄漏密钥?

```text
★ 不会。★ 密钥只在 Authorization 头里,★ 那个头不参与日志
★★ 但要注意:★ 这条日志打的是【完整的上游响应体】——
   ★ 生产环境要考虑它的体积和隐私,★ 见 待深入问题
```

### F3. 日志级别怎么调?

```text
★ application.yml:logging.level.io.github.maixiaowen.gateway: INFO
★ 排障时想更细 → 调到 DEBUG;⚠️ 生产别长期开 DEBUG
```
