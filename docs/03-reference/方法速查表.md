# 方法速查表

> **本页速览**
> - 按"**谁会调它**"组织,不是按字母序 —— ★ 查方法时你要的答案是"它为什么存在"。
> - ★★ 全项目**只有一个方法真正对外**:`RedisTokenBucketLimiter#tryAcquire` 之外的业务链路,都是从 `ChatController#completions` 进去的。
> - ★ 最容易看错的一个签名:`ChatController#completions` 返回 **`Object`**,不是 `Mono<…>` —— 原因见 §4。
> - ★★ `Provider` 接口只有 **3 个方法**,而整个网关的扩展性就靠这 3 个 —— 这是全项目最该背下来的。
> - ⚠️ 本页只列方法,不解释设计动机 → 动机在各自的类页里。
>

## ① ★★ SPI:3 个方法撑起整个扩展性

`com.example.gateway.provider.Provider`(接口,73 行)

| 方法 | 签名 | 谁调 | 备注 |
|---|---|---|---|
| `name` | `String name()` | `ProviderRegistry#indexByName` | ★ **注册表的 key,必须唯一非空** |
| `chatCompletion` | `Mono<ChatCompletionResponse> chatCompletion(ChatCompletionRequest)` | `ChatController#completions` | 非流式,**发一次收一次** |
| `chatCompletionStream` | `Flux<ChatCompletionChunk> chatCompletionStream(ChatCompletionRequest)` | `ChatController#streamToClient` | 流式,**发一次收多次** |

```text
★★ 三个方法的返回值形状就是"这个渠道能怎么用"的全部定义:
   ★ Mono = 最多一个结果   ★ Flux = 零到多个结果
   ↓
★ 而"多份配置用同一个实现"这件事,靠的是 ★ 实现类持有自己的字段
  (baseUrl / apiKey / defaultModel),★ 不是靠方法参数传进来
```

> ★ 接口边界为什么只有这三个 → [类-Provider](../01-modules/02-上游渠道抽象/类-Provider.md)

## ④ ★★ 限流链路:`tryAcquire` 的内与外

### `RedisTokenBucketLimiter`(237 行)

| 方法 | 访问 | 一句话 |
|---|---|---|
| `tryAcquire(String clientId)` | public | ★★ **唯一公开方法**:调 Lua 拿决策 |
| `parseDecision(String json)` | private | 解析 Lua 用 **`cjson`** 返回的结果 |
| `onLimiterFailure(String key, Throwable)` | private | ★★ **fail-open / fail-closed 的分叉点** |

### `RateLimitDecision`(102 行)

| 方法 | 一句话 |
|---|---|
| `RateLimitDecision(Outcome, long remaining, long retryAfterMillis)` | ★ record 主构造 |
| `static allowed(long remaining)` | 正常放行 |
| `static denied(long remaining, long retryAfterMillis)` | ★ 被拒 |
| `static unavailable()` | ★ Redis 挂了且 **fail-closed** |
| `static allowedWithoutQuota()` | ★★ Redis 挂了但 **fail-open** —— **放行,但水位未知** |
| `allowed()` | ★ 语义判断,不是 `outcome == ALLOWED` |
| `retryAfterSeconds()` | ★★ **向上取整**:`1399ms → 2`,而 `1000ms → 1` |

```text
★★ allowedWithoutQuota 是最容易被当成"多余"的一个工厂方法:
   ★ 它表达的是"放行 而且 我不知道还剩多少"
   ★★ 如果图省事复用 allowed(0),客户端会以为 ★ 额度刚好用完
   → 见 类-RateLimitDecision
```

## ⑤ 错误链路:异常变成响应

### `UpstreamExceptionHandler`(121 行)

| 方法 | 一句话 |
|---|---|
| `handleUpstreamFailure(Throwable e)` | ★ **兜底** —— 连不上 / 超时,判出 502 还是 504 |
| `handleUpstreamHttpError(WebClientResponseException e)` | 上游回了 4xx/5xx → ★ **一律 502** |
| `handleUnknownProvider(UnknownProviderException e)` | → ★ **400**(唯一一个"客户端错") |
| `build(HttpStatus, String message, String code)` | 统一造 `ResponseEntity<OpenAiErrorResponse>` |
| `hasCause(Throwable, Class<? extends Throwable>)` | ★★ **沿 cause 链找根因** |

```text
★★ hasCause 为什么必须存在?
   ★ Reactor 会把真实异常 ★ 包在好几层里传上来
   ★ 直接 instanceof 判断 → ★ 永远匹配不上 → 全走兜底分支
   → 表现:"超时都变成了同一个错误码",而 ★ 代码看起来完全正确
```

| `idleTimeoutMs()` | `UpstreamIdleTimeoutException` | ★ 带上超时值,便于日志定位 |

## ★ 名字像但完全不同的方法

### ① `resolve` vs `resolveOrDefault`

```text
resolve("kimi")          → ★ 不存在就抛 UnknownProviderException
resolveOrDefault("kimi") → ★★ 不存在也抛!两者对"不存在"的处理一样
   ↓
★ 真正的区别在 ★ null / 空白:
   resolve(null)          → 不值得调用(会抛)
   resolveOrDefault(null) → ★ 回落默认渠道
★★ 名字里的 "OrDefault" 指的是 ★ "没指定就用默认",不是 "找不到就用默认"
```

> ★★ 这个区别值钱:如果理解成后者,就会写出**静默回落**那个错误设计。
> ★ 见 [测试-路由与注册表](../01-modules/07-测试验证/测试-路由与注册表.md)。

### ② `chatCompletionStream` vs `chatCompletionStreamRaw`

| | 返回 | 做什么 | 谁调 |
|---|---|---|---|
| `chatCompletionStreamRaw` | `Flux<String>` | ★ **只管传输**:收行、超时、取消日志 | ★ `IdleTimeoutTest` **直接调它** |
| `chatCompletionStream` | `Flux<ChatCompletionChunk>` | ★ **三段式**:raw → 过滤 `[DONE]` → 归一 | `ChatController` |

```text
★★ raw 是 【public】 的,而不是 private —— ★ 这是一个刻意的设计:
   ★ 为了让"空闲超时会不会杀流"可以 ★ 绕开整条归一链路单独验证
   ★★ 规律:「能单独测的,一定是单独抽出来、并且可见性放开了的」
```

### ③ `normalize` vs `normalizeChunk`

| | 输入 | 缺字段怎么办 |
|---|---|---|
| `normalize(JsonNode, String)` | **一整份**响应树 | ★ 填默认值(`role` 缺 → `"assistant"`) |
| `normalizeChunk(String, String)` | **一片** SSE 原文 | ★★ **不填!** 缺就是缺(`hasNonNull` 判断) |

```text
★★ 同一个词"归一",两条路策略相反 —— 因为:
   ★ 一整份响应缺字段 = 数据不全,★ 该补
   ★ 一片流式缺字段 = ★ 缺本身就是信息(role 只在第一片)
```

### ④ `denied` vs `unavailable`

| 工厂方法 | Outcome | HTTP | 含义 |
|---|---|---|---|
| `denied(remaining, retryAfter)` | `DENIED` | ★ **429** | 你超了,**等一会儿再来** |
| `unavailable()` | `UNAVAILABLE` | ★ **503** | 我不知道你超没超,**限流器坏了** |

```text
★★ 两者都会"拒绝请求",但 ★★ 责任方和客户端该做的事完全不同:
   · 429 → ★ 客户端应该退避重试,并且 ★ 这是它自己的问题
   · 503 → ★ 应该告警运维,而且 ★ 客户端重试也没用
   ★ 混成一个码 = 把系统故障伪装成客户端限流
```
